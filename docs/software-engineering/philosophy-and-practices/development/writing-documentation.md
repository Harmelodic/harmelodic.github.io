# Writing documentation

Write stuff down! You will forget, and if its written down it can be shared with others.

Well written and discoverable documentation is always appreciated, and lack of documentation is always cursed.

I recommend writing two kinds of documentation:

1. Documentation that covers everything one needs to know to get stuff done (that links to external documentation when
   referring to 3rd party systems / things). This should be centralised and well-organised (e.g. in a handbook).
   Decentralising this kind of documentation just results in it being less discoverable. If you have problems with too
   much documentation, invest time and money in organising that documentation better and making it searchable.
2. System documentation that is stored alongside the code for the system. System-specific architectural decision records
   (ADRs) are especially useful.

Documentation as code can make it harder to edit documentation but easier to version control and alter how the
documentation gets rendered / hosted by not tying it to a specific platform.

Ensure you hire people who like writing documentation - they are surprisingly few and are immensely helpful, because a
lot of engineers don't like writing documentation and so just... don't, hence why "lack of documentation" is such a
prevalent problem.
